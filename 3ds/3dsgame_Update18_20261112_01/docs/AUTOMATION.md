# 自動実行の運用メモ

- 予約: 定期予約が本番。実行は6時間ごと(1回の「実装→テスト→保存」は2時間以内)。一回限りの予約は新しく作らない(重複実行になる)。予約の確認は「重複がないか見て報告するだけ」で、作り直し・新規作成・無効化はしない。
- 二重起動の防止: 実行開始時に親フォルダ直下の `_RUNNING.txt` を確認する。あり、かつ作成から3時間以内なら前の実行が終わっていないので、待たずに「前の実行中のため終了」と一言だけ報告して即終了する(待機・再確認・Monitor は使わない)。3時間より前の古い印は中断された古い印なので無視してよい(消せない場合は無視して続行する)。開始したら `_RUNNING.txt`(開始時刻JSTと実行名)を作り、最終報告の直前に必ず trash_file で消す。失敗して中断する時も消す。
- 保存先: Google Drive「マイドライブ/chat保存/3dsゲーム」(親フォルダID 1m6_xuL17_dACBy8YcLu1MLsDiXmNOO0I)。PCが繋がっていれば G:\マイドライブ\chat保存\3dsゲーム にも書く。
- 保存方式: zipは使わず、プレーンファイルのままフォルダ単位で保存する。
  - フォルダ名: 3dsgame_Update{2桁通番}_{YYYYMMDD}_{その日の何回目か2桁}(日付はJST)。通番は更新ごとに+1、末尾は同日の保存ごとに+1。
  - 中身: source/ tests/ tools/ docs/ と Makefile, README.txt, _INFO.txt(要約・テスト結果・次回予定)。
- 最新フォルダ = 通番NNが最大(同じNNなら末尾が最大)。同日に別実行が作った同じNNのフォルダが複数ある場合は末尾が最大のものを使う。保存直前に再検索して重複を避ける。
- 各回の流れ: テスト → 保存 → テスト → 保存 → テスト
  1. 最新フォルダをDriveから調べる(search_files の parentId 指定。ページ送りで同じ結果が返ることがあるので、title条件を足して絞ると確実)。
  2. docs の最新 DEVLOG_UPDATE{NN}.md の「次回の予定」から1〜3項目を実装。
  3. テスト① sh tools/run_tests.sh(取得できたファイル分)。
  4. 保存①: 新フォルダ作成、変更ファイルは create_file(textContent, text/plain, disableConversionToGoogleType=true)、未変更は copy_file。fileSize と wc -c を照合。_INFO.txt も置く。
  5. テスト② 保存物を再取得して再実行。
  6. 保存②: 最終修正があれば末尾+1のフォルダへ。
  7. テスト③ 最終フォルダで最終テストし短く報告。
  8. 予約の確認のみ(重複していないか見て報告だけ)。
- 注意:
  - read_file_content は整形(バックスラッシュ付与)されるためコード復元には使えない。コードは download_file_content(base64)を使い、デコード後に fileSize と照合する。ただし大きいファイル(game.c 35KB)は転記コストが大きい。
  - 取得するのは変更するファイルとテストに必要なファイルだけにし、残りは copy_file で引き継ぐ。
  - game.c に依存しない純粋ロジックは単体テストを別にビルドできる。
  - 禁止語は tools/private_blocklist.txt(1行1語)に書き、check_banned.py が検査する。元資料の実名はドキュメントやコードに書かない。
- 【禁止】虫の登場/他社作品の名称・素材/元資料の実名・実在地名。
